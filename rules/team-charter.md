# 虚拟开发团队公约（Team Charter）

本文件是 virtual-team 插件中**所有 agent 与 skill 必须遵守的全局规则**。

## 0. 开工前置（必读，单点声明）

任何角色在开始工作前，**必须依次读取**以下三份规则文件（本文件为唯一声明处，各处不再重复）：

| 规则文件 | 规定什么 |
|---------|---------|
| `rules/team-charter.md`（本文件） | **做什么、边界在哪**：角色纪律、编号规范、目录结构、评审闭环 |
| `rules/engineering-discipline.md` | **怎么做才可信**：证据先于结论、两阶段评审、完成状态协议、用户主权等 |
| `rules/decision-brief.md` | **怎么向用户提问**：决策简报格式（仅与用户交互的角色需要，如 product-manager / architect / project-manager） |

## 1. 角色纪律

1. **职责边界**：每个角色只做本职职责范围内的事，不越界。发现职责外的问题时，写入报告并转交对应角色，不自行处理。
2. **文件化输入输出**：角色的输入与输出一律以**文件**为载体（Markdown 为主），输出必须遵循 `templates/` 下对应模版的结构。
3. **禁止猜测**：不猜测、不假设。遇到不确定事项，**必须向用户提问确认**后再继续。
4. **工作目录纯净**：每个角色的产物只能写入其指定工作目录，目录内不得混入无关文件。临时文件、日志、中间产物统一放入 `build/` 或 `tmp/`，不污染交付目录。
5. **任务五步流程（强制，适用于所有角色的任何任务）**：
   **① 计划** → **② 与用户确认** → **③ 批准后实施** → **④ 校验结果** → **⑤ 任务完成报告**
   - **① 计划**：先产出计划/方案——写明做什么、产出物、验收方式。
   - **② 与用户确认**：以决策简报（`rules/decision-brief.md`）或计划文档形式与用户对齐。
   - **③ 批准后实施**：**未获用户明确批准不得开工**；批准须可追溯（消息/确认记录）。
   - **④ 校验结果**：完成后按计划中声明的验收方式**实际校验**——证据先于结论（`rules/engineering-discipline.md` §1）。
   - **⑤ 任务完成报告**：向派发方/用户报告——任务编号 + 产出物清单 + 校验证据 + 状态（DONE / DONE_WITH_CONCERNS / BLOCKED / NEEDS_CONTEXT，格式见 `rules/engineering-discipline.md` §8）。
   - **例外（简化处理）**：
     - 评审类角色（只读）的 ⑤ = 评审报告本身，④ = 逐项核对评审角度；
     - **微任务**（看板行更新、状态登记等）：② 与 ③ 可合并为一次交互，但**留痕不可省**；
     - 缺陷回归验证按 `case-running` 既定流程（⑤ = 回归 EXEC + BUG 状态回写）；
     - **子代理允许与用户直接交互（分级）**：任务范围内的信息澄清、实现计划确认（②③）可用 AskUserQuestion 直问用户；**方向性决策**（架构方向、接口契约变更、跨模块/跨任务影响、共享资源使用）须经项目经理。**任何冲突、歧义或多方答案不一致，均可直接提交用户决策**（用户主权优先，见 discipline §11）。交互结论**强制留痕**：写入完成报告"经用户确认：X"（**看板由 PM 唯一回写**，子代理不直接编辑看板——见下方"看板单一写者"）；并行实例的答案冲突由项目经理核对报告时仲裁。
     - **确认等待纪律（防挂起）**：子代理向用户发出确认请求后**不得无限等待、不得自行猜答案替代确认**——用户未响应即转 `NEEDS_CONTEXT` 报项目经理（附决策简报原文与已尝试内容）收束本任务；**不阻塞其他分片**。项目经理将各分片的待批项**汇总为一次批量决策请求**再问用户（减少碎片化打扰），拿到答复后逐分片释放。
6. **交付物须评审**：所有交付物必须经评审通过才算完成任务（评审人按阶段不同，见流程）。
7. **图形化用 Mermaid**：需要图形展示时，一律使用 Mermaid 语法（流程图、ER 图、时序图、状态图等）。
8. **看板单一写者（PM）**：`board/KANBAN.md` 是全局进度**唯一真相**，由 project-manager **唯一写入**——多子代理并行编辑同一文件会互相覆盖。各角色通过**产物文件 + 完成报告**传递状态（完成报告含状态自评与产出物路径），PM 核对后统一回写看板；TM 的缺陷登记落缺陷单/审定结论文件（缺陷派发记录由 PM 回写看板）。**子代理不得直接编辑看板**——发现看板信息过时或缺失，写入完成报告由 PM 更新。

## 2. 命名与编号规范

**层级模型**：`组件（component）` ⊃ `模块（module）`。**组件是划分与存放的主层级**；组件较小时可不细分模块（模块位用 `all` 占位，**保证编号恒为固定段数、可机械解析**）。

| 对象 | 规则 | 示例 |
|------|------|------|
| 项目名 | `$PROJECT_NAME` | `order-center` |
| 组件名 | `$COMPONENT`，**snake_case**（小写字母/数字/下划线，**禁含连字符**——连字符是层级分隔符） | `workbench`、`task_svc` |
| 模块名 | `$MODULE`，**snake_case**；组件不细分模块时用 `all` | `task_list`、`all` |
| 业务 | `biz-$COMPONENT-$MODULE-NNN` | `biz-workbench-task_list-001` |
| 功能点 | `fr-$COMPONENT-$MODULE-NNN`（固定 4 段）；前后台拆分时模块位取 `ui`/`svc` 或 `all` | `fr-workbench-task_list-001` |
| 测试用例 | `CASE-$COMPONENT-NNN`（用例属主组件；可跨组件引用功能点） | `CASE-workbench-001` |
| 测试数据单元 | `TD-$COMPONENT-NNN`（数据属主组件；可服务多用例） | `TD-workbench-012` |
| 执行轮 | `RUN-NNN`，度量的分母单位（**test-manager 创建**；跨组件，不加前缀） | `RUN-007` |
| 执行明细 | `{plan_ref}-{seq}`（如 `P-003-1`），追加式，回指实例行；plan_ref 全局唯一 → exec_id 全局唯一（并行分片零撞号） | `P-003-1` → P-003 |
| 实例计划行 | `P-xxx`，**全局唯一（跨 RUN，TM 审定时查重）**，EXEC 回指锚点 | `P-003` |
| 变更单 | `CR-$COMPONENT-NNN` | `CR-order-005` |
| 缺陷 | `BUG-$COMPONENT-NNN`，状态机闭环，回指 exec | `BUG-order-007` |

> **编号不可解析的写法**：`fr-task-svc-all-001` —— 组件是 `task` 还是 `task-svc` 无法判定。故组件/模块名**必须用下划线**（`task_svc`），连字符**只作层级分隔**。
> **主归属原则**：功能点严格属于「组件×模块」；用例与数据单元**有主组件**（编号体现），跨组件复用通过 `function_refs` / `dataset_refs` / `owner_cases` 数组表达。
> **永不复用**：编号一经分配不复用；废弃条目保留编号并标注「已废弃」及原因。

## 3. 标准目录结构

团队统一使用以下目录结构。各角色只在自己负责的目录内写文件。**组件/模块层级在目录上分层存放**。

```
$PROJECT_ROOT/
├── docs/                       # 立项与需求阶段交付物（PM / 产品经理）
│   ├── PROJ_$PROJECT_NAME.md   # 立项报告
│   ├── changes/                # 变更单 CR-$COMPONENT-NNN.json（变更管理，见 §5.1）
│   └── requirements/
│       ├── overview.md         # 业务分析概览
│       ├── dict.md             # 数据字典（全局）
│       ├── spec-nonfunc.md     # 非功能需求说明书
│       ├── RTM.md              # 需求追踪矩阵（含「页面/原型」列，与页面×FR覆盖矩阵合并维护）
│       └── $COMPONENT/         # ★ 按组件分层
│           └── $MODULE/        #   （组件不细分模块时可省略此层，文件直接放组件目录）
│               ├── biz.md      # 业务分析说明书
│               ├── spec.md     # 软件规格说明书（前后台拆分：spec-ui.md / spec-svc.md）
│               └── trace/req.json  # 结构化需求分片
├── design/                     # 设计阶段交付物（架构师）
│   ├── ARCH.md
│   ├── DATABASE.md
│   ├── FUNC.md
│   ├── DATASTRUCT-ALGORITHM.md
│   ├── INTERFACE.md
│   ├── LOGGER.md
│   └── DEV-TASKS.md            # 开发任务分解（规划物，设计评审通过后产出）
├── src/                        # 源代码（开发工程师）
│   └── $COMPONENT/             # 与组件对齐
│       └── code + tests/       # tests/ = 单元测试
├── review/                     # 评审报告（评审员）
│   ├── requirement/
│   ├── design/
│   ├── code/
│   └── project/
├── test/                       # 测试阶段（测试经理 / 测试工程师）
│   ├── STORE-CONFIG.json       # ★ 存储轨道开关（json|sqlite，PM 立项时创建经用户确认，唯一开关）
│   ├── plan.md                 # 测试方案
│   ├── baseline/               # 环境基线（TM 定义：初始化脚本/种子数据/恢复方式；TE 搭环境时执行——基线=部署级初始态，TD=用例级数据）
│   ├── cases/$COMPONENT/       # 测试用例 CASE-$COMPONENT-NNN.md（按组件分层）
│   ├── data/$COMPONENT/        # 数据单元：JSON 轨=TD-$COMPONENT-NNN/；SQLite 轨=数据入业务表 td_biz_*
│   ├── automation/             # 自动化脚本（CASE.automation.script_ref 指向）
│   ├── runs/                   # 执行轮（JSON 轨：RUN/EXEC-PLAN/EXEC；SQLite 轨入 metrics.db）
│   ├── bugs/                   # 缺陷单（JSON 轨；SQLite 轨入 metrics.db）
│   ├── trace/$COMPONENT/       # 结构化数据：JSON 轨=case-<组件>-<模块>.json 分片 + TD 注册表分片；SQLite 轨=metrics.db
│   └── report/                 # 度量报告（test-rebuild 派生，两轨同格式）+ 评估报告
├── release/                    # 发布阶段（发布工程师）
│   ├── artifact/               # 发布组件
│   ├── manual-install.md       # 安装手册
│   └── manual-release.md       # 发布手册
├── pages/                      # 界面原型（产品经理）
│   └── prototype/
├── templates/                  # 交付物模版（本插件提供）
├── board/                      # 进度看板（项目经理）
│   └── KANBAN.md
└── build/                      # 构建产物 / 中间文件（禁止写入交付目录）
```

## 4. 评审闭环

任何评审（需求/设计/代码/测试/项目）都必须形成闭环：

```
评审员产出报告 → 报告项目经理 → 项目经理派发责任角色修订 → 修订完成报告 → 评审员验证 → 关闭
```

- **消息经项目经理中转**：评审员是子代理、无消息通道，不得直接"发送"给责任角色；评审结论一律写文件 + 报告项目经理，由项目经理 spawn 责任角色修订、再派评审员复验。
- 评审报告须指明：**文件 + 组件/模块 + 功能编号**，缺陷按 `P0/P1/P2` 分级。
- 未关闭的 P0/P1 缺陷不得进入下一阶段。
- 评审员**只读代码/文档，不得修改**。必要时可以运行验证，但不得改动被评审物。

## 5. 阶段与门禁

```
立项 → [立项评审] → 需求分析 → [需求评审] → 架构设计
     → [设计评审] → 架构师分解(DEV-TASKS) → [分解评审] → PM指派
     → PM派发(spawn开发者) → 开发完成 → 开发者向PM报告(含状态自评,PM回写看板)
     → [代码评审] → [测试版构建] → 测试准备(用例+数据单元，可与编码并行；TM建RUN头)
     → 实例化(TE配对) → [TD注册表+实例计划审定] → 执行RUN(EXEC→BUG)
     → 回归闭环 → [度量评估] → [项目验收] → [生产版发布]
```

- **分解评审并入设计评审**（同一门禁、同一评审员），不单独增设门禁。
- **顺序不可颠倒**：设计评审通过 → 架构师修订设计 → 产出 `design/DEV-TASKS.md` → 分解评审。
  在未定稿的设计上先分解，设计一改则分解全部作废。
- **阶段边界**：设计阶段以"设计评审（含分解评审）通过"结束；开发阶段以"PM 指派并派发"开始。
- **完成闭环**：开发者完成 → 更新看板状态 + 向 PM 报告 → PM 核对验收标准 → 组织代码评审。
- **测试版构建（测试准入条件）**：代码评审全部闭环（无未关闭 P0/P1）后，由 release-engineer 用 `skills/releasing` 的构建流程产出——全新 worktree 从主干构建 → 打包归档 → 产出安装/发布手册 → 部署冒烟验证 → 标记**测试版**。测试环境一律来自该构建产物（RUN.envs 的 build/commit 引用它）。测试期缺陷修复后须重新构建（回归轮 envs 引用新 build）。
- **生产版发布**：项目验收通过 + 四方联合确认 → 打 tag；测试期无代码变更可直接升级标记，有变更须重新构建再确认。
- **RUN 头归 test-manager**：TM 建头（trigger/scope/envs/defect_refs）→ TE 在既定 RUN 内配对实例 → TM 审定 → PM 派发执行。RUN 头为**纯计划态**（无 summary/finished_at）——轮次汇总由 `test-rebuild` 从 EXEC 派生，不回写。
- **测试执行门禁**：TD 注册表与**实例计划 EXEC-PLAN** 未经 test-manager 审定不得执行；EXEC 只追加不改写；缺陷关闭须 verify_pass 证据。

### 术语

- **分解**：架构师把设计拆成可独立开发与验收的任务，产出 `design/DEV-TASKS.md`（**规划物**）。
- **指派**：确定任务的具体执行人、优先级、排期，并落入看板（**项目管理环节**）。
- **派发建议**：技术侧给出的**决策输入**——架构师对开发任务（建议执行角色 + 并行组 + 串行化提示）、测试经理对测试分片（分片 → 建议 test-engineer 实例 + env 分配）。与派发动作分离。
- **派发**：**运行期把任务真正交给执行者**——由项目经理持有 `Agent` 工具，spawn 执行子代理并注入自包含任务输入。派发权**唯一归项目经理**（依据派发建议做最终裁决 + 冲突仲裁）。

> 说明 1：`statement.txt` 将"工作任务指派"列为项目经理职责；本插件沿用——架构师负责**分解**（技术判断），项目经理负责**指派 + 派发**（项目判断 + 执行调度）。
>
> 说明 2：**执行派发权唯一归 PM**。其他角色（含主代理代演的场景）不得越权 spawn 执行角色；发现该派未派的任务，写入看板提醒 PM。
> 说明 2b：**主代理（编排者）代演规则**——主代理不持有 PM 职权。流程需要 spawn 执行角色而 PM 不在场时，**先 spawn project-manager** 由其履行派发；仅当用户**显式指示**主代理代演某角色时视为临时授权（须留痕：谁授权、代演哪个角色、起止），且代演产物同样过对应评审门禁，不因代演豁免质量要求。
>
> 说明 3：**完成报告闭环**——开发者完成任务后：① **commit 到主干**（message 含任务编号；未 commit 不得报完成，见 discipline §13）；② 向项目经理报告（任务编号 + 改动文件 + commit hash + 状态自评 + 验证结果——**不直接写看板**，charter §1.8）。PM 收到后核对验收标准与 commit、**回写看板**、组织代码评审。
>
> 说明 4：**建议权与动作权分离**——技术侧（架构师、测试经理）提供**派发建议**（决策输入），项目经理执行**派发动作**（spawn）并做冲突仲裁、优先级与排期。为什么不把派发权下放给技术/测试 leader：子代理之间无消息通道，多 spawn 点会失去单一信息枢纽、无法天然仲裁共享文件 / env 冲突。

## 5.1 变更管理（CR 五步闭环）

范围外的需求/设计/代码/测试资产变更（`CR-$COMPONENT-NNN`，模板 `templates/CR.json`，存放 `docs/changes/`）走以下闭环；**缺陷修复走 BUG 状态机、评审打回走评审闭环，均不走 CR**：

```
① 提出登记 → ② 影响评估 → ③ 用户批准 → ④ 实施与同步 → ⑤ 校验关闭
```

| 步骤 | 动作 | 责任 |
|------|------|------|
| ① 提出登记 | 任何角色发现需变更时**报项目经理并停手**（不直接改文档）；PM 建 CR 单登记（draft） | 提出角色 → PM |
| ② 影响评估 | PM 按涉及面派发对应角色列影响清单（受影响 fr/biz/case/TD/文档章节 + 范围/工作量/风险评估），回填 CR（assessing） | 产品经理（需求）/ 架构师（设计）/ 开发（代码）/ 测试（资产） |
| ③ 用户批准 | PM 汇总评估结论，**用户批准后**才进入实施（用户主权；拒绝 → rejected 归档） | 用户 |
| ④ 实施与同步 | 责任角色修订产物（spec/设计/代码），**下游同步**：需求变更 → `req-structure` 重跑（acceptance 只追加 key）→ case/TD 对齐；设计/代码变更走既有评审门禁（implementing） | 责任角色 |
| ⑤ 校验关闭 | PM 核对：`test-rebuild` 源同步无 stale、评审门禁通过 → closed | PM |

## 6. 缺陷分级

| 级别 | 定义 | 处理 |
|------|------|------|
| P0 | 阻塞性缺陷，功能不可用、数据错误、安全漏洞 | 必须修复，阻塞发布 |
| P1 | 严重缺陷，主要功能受损但可绕过 | 必须修复，阻塞发布 |
| P2 | 一般缺陷，体验问题 | 可排期修复 |

## 7. 交付物质量红线

- 需求：功能点必须可独立验收，且验证标准**条列化 + GWT 化**（每条 `{key, given, when, then, kind}`），并**按生成清单逐类对照**（正常/边界/异常/权限校验/输入校验/状态约束，按适用性取舍）——供测试点级覆盖度量。
- **FR 粒度（L2）**：一个 FR = 单一触发 → 单一可观察结果的完整行为闭环；粒度经**五条检验**（含「以及/同时还要」即拆、多个不相干 `when` 即拆、L4 细节降层）。**禁止"部分完成"语义**——粒度不合适须拆分，不得降粒度凑整。
- **L4 归属**：交互/视觉细节（按钮态、文案、动效、颜色、布局）**禁止写入 FR**，归原型与交互说明。
- **前后台边界**：**前台 PRD** 只约束 UI 行为与前端校验，业务规则一律用 `【占位：待<服务名>PRD 补充·<规则名>】` 引用，**不自定义规则**；**后台服务 PRD** 约束业务规则、数据模型与接口契约，**不写 UI**；同一页面在两份 PRD 中各自沿自己的轴切分，内容不重叠、编号不重复。
- **跨产物一致性（交付前强制对账）**：凡同时交付 PRD 与页面原型的任务，交付前必须产出**「页面 × FR 覆盖矩阵」**（并入 RTM）——原型每个页面 × 每个主要操作必须挂到 ≥1 条 FR（或占位符引用）；**矩阵出现空白（页面/操作无 FR 承接）→ 不得交付**（补 FR 或删原型元素，二者必居其一）。出稿自检须含跨产物核对（PRD ↔ 原型 ↔ RTM 三者互查），不得只查文档内部结构。
- 设计：设计条目必须能与**功能编号**关联。
- 任务分解：任务可独立开发与验收，依赖**无环**，功能编号**全覆盖**。
- 代码：遵循**最简代码原则**，用最简单的代码实现功能。
- 测试：测试用例必须覆盖**所有功能点**；每条 active 用例必须有**数据单元支撑**（无 TD = 假覆盖）；用例应**逐条覆盖功能点的全部验证条件**（`acceptance_refs`），未覆盖须显式说明理由。**测试点级覆盖率仅作度量，不作硬门禁**；测试通过标准为 **无 P0/P1 遗留**。
- **模板纯净性**：`templates/` 下所有文件的**结构、字段、机制说明**不得包含业务域概念（业务概念只允许出现在**示例/演示内容**中，如 ER 图示例 `USER/ORDER`、日志示例、时序图参与者——示例是教学内容，不算违规）。判定标准：把示例删掉后，剩余骨架是否仍完整表达该交付物的结构；若结构本身依赖某个业务概念才成立，才是违规。
- **TD 黑盒**：测试数据单元对机制层只暴露 `{id, description, load_entry}`；description **禁止**写入 expected（预期属执行计划配对行）与业务字段值；数据本体留在单元内部，机制不解释。**`suitable_for` 值域 = normal/boundary/negative**（与需求侧 `acceptance.kind` 同枚举）——它是 `case-instantiate` 逐条件配对的匹配键（实例计划的 `condition` 的 kind 须 ∈ TD.suitable_for）；混合场景底座用数组多值表达，不设 combination。
- **关联双向一致**：TD 的 `owner_cases` 与用例侧 `dataset_refs` 必须双向一致；共享数据单元的影响面 = 全部 owner_cases，改数据语义须评估所有 owner。
- **测试执行分片**：测试任务（用例设计/数据生成/执行）**按「组件」分片**，可多 test-engineer 实例并行；**执行分片 = 组件**（一组件一分片一文件），**env 为执行期独占租用资源**，同一 env 同一时刻只允许一个分片占用（**同时活跃分片数 ≤ RUN.envs 数**）；实例只写本分片产物，注册表/实例计划由 test-manager 审定。
- **组件/模块层级（主归属）**：功能点严格属「组件 × 模块」（`fr-$COMPONENT-$MODULE-NNN`，固定 4 段，组件无模块时用 `all` 占位）；用例（`CASE-$COMPONENT-NNN`）与数据单元（`TD-$COMPONENT-NNN`）**有主组件**（编号体现），**跨组件复用通过 `function_refs` / `dataset_refs` / `owner_cases` 数组表达**——主归属不限制复用。组件名/模块名一律 **snake_case**（连字符只作层级分隔符），保证编号可机械解析。目录按组件/模块分层存放。
- **存储轨道纪律**：测试数据存储为双轨（json / sqlite），**项目立项时一次性选定**（project-manager 与用户确认，写入 `test/STORE-CONFIG.json`——唯一开关），**全程跟随、禁止两轨混写、禁止默认选轨、仅允许一次 json→sqlite 单向迁移（迁移后不可逆）**。SQLite 轨下 `test/trace/metrics.db` 为唯一权威存储（五方机制数据 + TD 业务数据全部入库；**业务表必含 `td_id` 外键关联 `td_registry`**——无关联的业务数据行 = 孤儿，P0）；`execs` 只追加（库级触发器禁 UPDATE/DELETE）；加载脚本仍单独存文件。

## 8. 发布状态

- **测试版**：未经产品经理、测试经理、架构师、代码评审员联合确认的版本（由 release-engineer 在**测试版构建**环节产出，作为测试环境来源）。
- **生产版**：经上述四方联合确认、打标签（tag）后的版本（项目验收通过后发布）。
- 发布构建必须使用**全新 worktree**，从 git 主干拉取、从头构建。
