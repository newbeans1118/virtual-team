# 通用设计（general-design）

## 目的

在全局架构与数据库设计确定后，产出**组件级功能设计**（含算法与日志事件）、**组件接口**，以及**全局接口契约与日志规范**。

## 执行者

`architect`

## 输入

- `docs/prd/$COMPONENT/$MODULE/prd.md`（按组件/模块）
- `design/ARCH.md`、`design/DATABASE.md`（全局数据规范）、`design/$COMPONENT/database.md`（本组件表结构）

## 输出

| 文件 | 层级 | 模版 | 内容 |
|------|------|------|------|
| `design/INTERFACE.md` | 全局 | `templates/INTERFACE.md` | 横切契约（版本/兼容/幂等/分页/限流/超时/重试/熔断/错误分类/租户）+ 组件接口索引 |
| `design/LOGGER.md` | 全局 | `templates/LOGGER.md` | 日志格式/目录/级别/脱敏/保留（**不写模块事件**） |
| `design/$COMPONENT/interface.md` | 组件 | `templates/INTERFACE-COMP.md` | 对外接口 + 跨模块接口 + 模块内接口 |
| `design/$COMPONENT/func.md` | 组件 | `templates/FUNC.md` | 功能设计 + FR 映射 + 算法 + 日志事件 |

**FUNC 拆分规则**：以架构已划分的模块边界（`$MODULE`）为基本单位、以高内聚为硬约束：
- 组件 `func.md` 默认按架构给出的 `$MODULE` 拆为 `design/$COMPONENT/$MODULE/func.md`；架构未划分子模块（单模块组件）则不拆。
- **高内聚优先**：不得为压行数/FR 数把同一高内聚功能单元拆散，也不得为凑阈值强行合并本应独立的模块。
- **FR 数 / 行数 是审视信号，非硬限**：单模块 FR 偏多或内容过长时，提示回架构确认模块边界是否该进一步细分；未达阈值但架构已明确划分子模块，仍应按模块拆。
- 拆分后**不再保留组件级 func.md**（禁止双写）。

## 内容要求

四份文件以对应模板为准（见上方输出表"模版"列），下列为强制规则，模板不重复赘述：

- **全局 INTERFACE.md**：横切契约（版本/兼容/幂等/分页/限流/超时/重试/熔断/错误分类/认证与租户）全局只有一份，组件不得另立；具体接口不在本文件展开，避免单文件膨胀。
- **组件 interface.md**：每个接口必须标注关联功能编号；对外/对内分开；标注可反查（被哪些 FR 调用、动哪些数据结构）；异步消息须定义 schema/顺序/重复保证；模块内接口仅在需跨开发者约定时填写。
- **组件 func.md**：FR 须逐条有落点，未覆盖须在“追溯与缺口”写明理由；功能设计每步标注事务边界，涉及状态迁移须给出状态机+持久化时机+补偿触发；异常路径按业务复杂度覆盖（高并发核心必含幂等/并发/超时）；处理流程 Mermaid 按需（仅功能涉及 ≥2 次状态迁移或跨模块/跨组件调用时必填，见 `rules/team-charter.md` §5）；日志事件只声明事件/级别/字段/脱敏，格式规范引用全局 `LOGGER.md`，不重复。
- **全局 LOGGER.md**：只定义日志规范（目录/格式/级别/脱敏/保留），明确打点位置（入口/出口/状态变更/外部调用/异常捕获/慢路径），按需定义体积上限/采样/告警关联；**不写各模块事件清单**（在对应 `func.md` §5）。

## 工作流

1. **收输入**：确认 `docs/prd/`、`design/ARCH.md`、`design/DATABASE.md` 及本组件 `database.md` 就绪；组件清单须来自架构设计输出。
2. **按组件产出**：套用对应模板逐组件写 `interface.md` 与 `func.md`（按架构模块边界拆分、禁止双写）；全局 `INTERFACE.md`/`LOGGER.md` 按模板填横切契约与规范。
3. **FR 覆盖核对**：逐条 FR 在 `func.md` 有落点，未覆盖在"追溯与缺口"写理由；接口与功能编号互相关联。
4. **设计者自检**：按下方"设计者自检门禁"逐条自过。
5. **移交评审**：自检通过后转 `design-review` 走设计评审门禁（修订 → 评审员验证 → 关闭，闭环经 PM 中转）。

## 质量要求

- 所有设计可追溯到功能编号；无对应功能的接口/结构不写。
- 接口契约完整，异常路径与错误码必须定义。
- 全局横切契约只有一份，组件接口不得与之冲突。
- 日志不得记录敏感信息明文。
- 每个功能点至少有一条可测后置断言，区分【自动化可验证断言】与【人工评审断言】（写在 `func.md` §3）。

## 设计者自检门禁

> 本门禁由 architect 交付前逐条自过；通过后**转 `design-review` 走设计评审门禁**（设计修订 → 评审员验证 → 关闭，闭环经 PM 中转）。

- [ ] 全局 INTERFACE 含横切契约与组件接口索引（索引列各组件 `design/$COMPONENT/interface.md`，模板见 `templates/INTERFACE.md`）
- [ ] 每个组件有 interface.md 与 func.md（或按模块拆分的 func.md）
- [ ] 每条 FR 在设计中有落点；未覆盖已写理由
- [ ] 满足复杂判据的流程有算法设计（在 func.md 内）
- [ ] func.md 含日志事件表
- [ ] 组件接口与全局横切契约一致
- [ ] 每个功能点至少一条后置断言（自动化/人工）

## 触发与边界

**该用**：架构与数据库设计确定后，做组件级详细设计。

**轻量档（见 `rules/team-charter.md` §9）**：指评审强度，不等同于文件组织。单组件、FR ≤ 12 的组件按其架构模块边界组织 `func.md`（无子模块则不拆），全局 INTERFACE/LOGGER 可精简；**每个组件仍须有 `func.md`（FR 可追溯性红线，不可省）**。高风险/核心/受监管组件不论 FR 数量，均须产出完整分层并过 `design-review`。注意：拆分规则（是否按 `$MODULE` 拆文件）由架构模块边界与高内聚约束决定，与是否轻量档无关。

**不该用**：
- 定架构与选型 → 用 `architecting`
- 设计数据库 → 用 `data-modelling`
- 评审设计 → 用 `design-review`

## 常见错误

- 仍按旧的单文件设计产出（FUNC/算法各一份，已废弃）。
- 组件接口另立一套版本/幂等规则，与全局 INTERFACE 冲突。
- FUNC 拆分后同时保留组件级文件（双写）。
- 接口只写正常路径，不定义异常与错误码。
- 日志记录敏感信息明文（违规）。
- 算法设计不给复杂度与边界条件。
- 功能设计复述 PRD 原文（"PRD 换皮"）——只写实现步骤，来源用编号引用。
- 日志设计虚化：只写"记录关键日志"，无级别/字段/打点位置。
- 只写 happy path：按业务复杂度该覆盖的异常（幂等/重试/超时/并发/降级）不写。
