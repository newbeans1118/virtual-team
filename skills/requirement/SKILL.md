# 需求分析（requirement）

## 目的

生成需求规格说明书，使业务分析落地为可实现、可验收的功能需求。

## 执行者

`product-manager`

## 输入

- `docs/requirements/overview.md`、`docs/requirements/biz-$MOD.md`
- `docs/PROJ_$PROJECT_NAME.md`

## 输出

- `docs/requirements/spec-$MOD.md`（模版 `templates/SPEC-MOD.md`）
- `docs/requirements/spec-nonfunc.md`（模版 `templates/SPEC-NONFUNC.md`）
- `docs/requirements/dict.md`（模版 `templates/DICT.md`）

## 流程

1. **功能点定义**：为每个功能点定义 —— 编号 `fr-$MOD-xxx`、功能名称、操作的用户、输入、输出、处理逻辑、约束条件、**验证标准**（可独立验收）。验证标准必须**条列化**——拆成一组可判定的条件条目（每项含 `key`/`text`/`kind`，见 `req-structure` 的 acceptance 结构；`kind ∈ normal/boundary/negative`）。**整段文本的验证标准不合格**——无法逐条核对覆盖。
   - 生成条件时**对照下方「acceptance 条件生成清单」**，按适用性取舍（不适用的类别可省略，但**省略应有理由**）。
2. **业务-功能关联**：为每个 `biz-xxx` 说明由哪些功能点、如何实现，产出一张关联矩阵。
3. **功能归模块**：按关联紧密程度把功能分配到模块。
4. **数据字典**：定义业务实体、字段、类型、约束、状态枚举。
5. **非功能需求**：安全需求、性能需求（量化指标）。
6. **一致性校验**：确认所有 biz-xxx 均被 fr 覆盖。

## acceptance 条件生成清单（逐类对照，按适用性取舍）

生成一个功能点的 acceptance 时，**逐类自查**；不适用的类别可省略（省略须在条件列表外一句说明，如"本功能无权限维度"）。类别是**写作思维提示**，最终 `kind` 仍只能取 `normal/boundary/negative`（下表给出映射）。

| # | 类别 | 说明 | 归入 kind |
|---|------|------|-----------|
| 1 | **正常路径** | 主流程成功，输入合法且状态允许 | `normal` |
| 2 | **边界值** | 数值/长度/时间/容量的临界（最小值、最大值、越界各一） | `boundary` |
| 3 | **异常路径** | 非法输入、错误状态、依赖失败等失败路径 | `negative` |
| 4 | **权限校验** | 有权限应通过 / 无权限应被拒 / 越权应被拦 | `normal`（通过）/ `negative`（拒绝） |
| 5 | **输入校验** | 必填缺失、格式错误、超长、类型不符 | `negative`（非法）/ `boundary`（临界） |
| 6 | **状态约束** | 非法状态迁移应被拒（如未审核不可发布） | `negative` |

> **取舍原则**：只写"该功能点自己该验的行为"。系统级的安全/性能约束（加密算法、防注入机制、审计日志格式）**不写在此处**——它们属 `spec-nonfunc.md` 的 `NF-S-xxx`/`NF-P-xxx`。
>
> **示例**（用户注册功能点）：
> ```
> c1 (normal)   合法邮箱+合规密码 → 注册成功且落库
> c2 (boundary) 邮箱长度=254（上限）→ 仍可注册
> c3 (negative) 邮箱已占用 → 拒绝且不落库
> c4 (negative) 未登录访客调用管理接口 → 403 拒绝        ← 权限校验
> c5 (boundary) 密码长度=7（低于下限8）→ 拒绝            ← 输入校验
> ```

## 质量要求

- 功能点"可独立验收"是硬门槛：无法验收的不要列为功能点（降级为约束或说明）。
- 每个功能点必须有**验证标准**，且**条列化**（一组可判定条件，各带 `kind`）——测试工程师据此出用例，`test-rebuild` 据此算测试点级覆盖。**整段文本不合格**。
- **acceptance 条件按「生成清单」逐类对照**（正常/边界/异常/权限/输入校验/状态约束），不适用的类别可省略但须有理由；漏掉适用类别 = 需求不完备。
- 规格必须**覆盖**业务分析的全部内容（追溯完整）。
- 非功能需求"不遗漏、不过分"：性能指标须有依据。

## 输出：追溯矩阵（示例）

| 业务编号 | 业务名称 | 覆盖功能点 | 模块 |
|---------|---------|-----------|------|
| biz-001 | 用户注册 | fr-user-auth-001, fr-user-auth-002, fr-user-auth-003 | user-auth |

## 检查清单

- [ ] 所有 biz-xxx 被 fr 覆盖（矩阵无空行）
- [ ] 每个功能点有验证标准，且**条列化**（key/text/kind）
- [ ] acceptance 条件**按生成清单逐类对照**（正常/边界/异常/权限/输入校验/状态约束），不适用类别已说明理由
- [ ] 数据字典与业务实体一致
- [ ] 非功能需求量化
- [ ] spec 覆盖 biz 全部内容

## 触发与边界

**该用**：业务已分析清楚，要把它转成可实现、可验收、可追溯的功能需求。

**不该用**：
- 业务还没建模 → 先用 `business-analysis`
- 要评审需求 → 用 `requirement-review`
- 要结构化存储功能点供追踪 → 用 `req-structure`

## 常见错误

- 功能点"不可独立验收"却列为功能点（应降级为约束或说明）。
- 功能点没写**验证标准**，测试无法出用例。
- **acceptance 只写正常路径**，漏边界/异常/权限/输入校验/状态约束（对照生成清单逐类自查）。
- 有 biz 无对应 fr（追溯断裂），或凭空加 fr。
- 非功能需求不量化（"性能要好"无意义）。
