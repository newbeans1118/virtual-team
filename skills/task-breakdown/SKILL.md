# 开发任务分解（task-breakdown）

## 目的

把**已通过设计评审的**设计，拆解为可由不同开发者独立开发与验收的任务，并梳理依赖与并行关系。

**这是"按模块切分开发任务"的专用技能，不是通用任务分解器。**

## 执行者

`architect`

## 输入

- `design/ARCH.md`、`FUNC.md`、`INTERFACE.md`、`DATABASE.md`
- 各组件/模块 `prd.md`（功能编号来源）

## 输出

- `design/DEV-TASKS.md`（模版 `templates/DEV-TASKS.md`）

## 前置（硬性）

1. **设计评审已通过**。
2. **设计已按评审意见修订完毕**（如有）。

> 若在旧设计上先分解，设计一旦被打回，分解结果全部作废。**顺序不可颠倒。**

## 切分原则

1. **以模块为单位**：任务边界与模块边界一致，不跨模块切。
2. **可独立开发与验收**：每个任务完成后应能单独验证——FR 任务验证其功能编号，ENABLER 验证其 DoD；不依赖其他任务的中间产物。
3. **依赖显式**：任务间依赖必须列出；**禁止循环依赖**。
4. **可追溯**：每个任务标注其覆盖的 `fr-$COMPONENT-$MODULE-NNN`。
5. **粒度适中**：
   - 过粗 → 无法并行、无法独立验收（一个任务塞了整个模块的全部功能）
   - 过细 → 任务间依赖爆炸、协调成本高于收益
   - 判据：**一个任务 = 一组紧密相关、可独立验收的功能编号**
6. **类型二分**：`FR`（覆盖功能编号，按功能验收）与 `ENABLER`（技术使能项：verify/CI、DB 迁移、可观测性接入、构建优化、脚手架）。ENABLER 不挂 FR，但必须有独立 DoD——否则 CI/迁移/可观测性会漏到上线前才补。

## 流程

1. 逐个模块读取设计，识别模块内的功能单元。
2. 识别**技术使能项**（verify/CI、DB 迁移脚本、可观测性接入、构建/脚手架）→ 标 `ENABLER`，写独立 DoD。
3. 按"可独立验收"聚合成 FR 任务，标注覆盖的功能编号。
4. 推导任务间依赖（数据依赖、接口依赖、部署依赖、使能依赖）。
5. 做拓扑排序，**检查无环**。
6. 按拓扑层级划分**并行组**（同组无相互依赖）。
7. 为每个任务给出**派发建议**（后端逻辑 → backend-developer；界面交互 → ui-developer）+ 需串行化的共享文件点。
8. 为每个任务标注**类型**（FR / ENABLER）与**相对规模**（S / M / L，规划输入，不是排期）。
9. 做覆盖性校验（FR 功能编号全覆盖、ENABLER 有 DoD、依赖环、可独立验收）。
10. 产出 `design/DEV-TASKS.md`，提交设计评审（分解评审并入设计评审）。

## 约束

1. **只分解，不指派执行**：本技能产出**规划物 + 派发建议**。给出"建议执行角色 + 并行组 + 串行化提示"（决策输入），但"谁做、何时做、优先级、spawn"属项目管理环节，不在本技能范围。
2. **不给优先级与排期**：那些依赖执行态信息，属于项目管理判断；但须给**相对规模 S/M/L**（规划输入）。
3. **必须与设计一致**：任务划分不得偏离 `FUNC.md` 的模块与功能划分；发现设计缺陷写入报告转交，不自行改设计。
4. **图形用 Mermaid**：依赖拓扑一律 Mermaid `flowchart`。

## 质量要求

- 每个任务标注 `任务编号 / 类型 / 规模 / 模块 / 覆盖功能编号 / 依赖 / 派发建议 / 并行组 / 串行化提示 / 验收标准（DoD）`，缺一不可。
- 依赖拓扑**无环**。
- **所有功能编号都有 FR 任务覆盖**（ENABLER 不计入功能覆盖）。
- 每个 ENABLER 有可验证的独立 DoD。
- 并行组划分正确：**同组内任务两两无依赖**。

## 触发与边界

**该用**：设计定稿后，需要把设计变成"可分配给不同人做的任务"时。

**不该用**：
- 设计还没通过评审 → 先完成 `design-review`
- 要定优先级/排期/指定到人 → 属项目管理环节，不在本技能
- 要做需求层面的功能拆解 → 用 `prd`

## 常见错误

- 在设计评审**之前**就分解（设计一改，全废）。
- 任务与模块边界不一致，切出跨模块的"大杂烩任务"。
- 依赖不写或写了**循环依赖**（并行的前提被破坏）。
- 任务过细（每个函数一个任务）→ 依赖爆炸。
- 顺手写优先级/排期（越界，属项目管理）。
- 有功能编号没被任何任务覆盖（校验表形同虚设）。
- 只拆 FR 任务，漏掉 CI/迁移/可观测性等使能项（上线前才补，风险最高）。

## 检查清单

- [ ] 前置满足（设计评审通过、设计已修订）
- [ ] 任务以模块为单位，边界清晰
- [ ] 每个 FR 任务覆盖明确的功能编号；ENABLER 标注无 FR 与独立 DoD
- [ ] 每个任务可独立开发与验收
- [ ] 依赖已列出且**无环**
- [ ] 并行组划分正确
- [ ] 所有功能编号被 FR 任务全覆盖
- [ ] ENABLER 已识别且有独立 DoD
- [ ] 每个任务标注类型与相对规模
- [ ] 未越界写优先级/排期
- [ ] 已提交设计评审（含分解评审）
