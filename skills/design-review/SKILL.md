# 设计评审（design-review）

## 目的

评审设计的正确性、合理性、完备性，产生评审文档。

## 执行者

`design-reviewer`（评审人另含**用户**）

## 输入

- `docs/prd/`
- 全局：`design/ARCH.md`、`ARCH-NFR.md`、`DATABASE.md`、`INTERFACE.md`、`LOGGER.md`
- 按组件：`design/$COMPONENT/database.md`（表结构/DDL/迁移）
- 按组件：`design/$COMPONENT/interface.md`、`design/$COMPONENT/func.md`（或 `$MODULE/func.md`）

## 输出

- **按组件**：`review/design/RV-DESIGN-$COMPONENT-xxx.md`（由 PM 汇总全部组件结论）

## 评审角度

1. 技术选型合理性（满足需求、不过度设计、依赖必要）
2. 架构与组件设计正确性（分层、职责、交互闭环）
3. 数据库设计（全局规范与组件表结构分层、组件未复制全局规范、跨组件外键在全局登记、索引合理、DDL 与字典一致；存量/结构变更须含 expand-contract 迁移与回滚）
4. 功能设计完备性（功能编号全覆盖）
5. 接口设计（契约完整、异常路径定义；横切契约齐全：版本/兼容/幂等/超时/重试/限流/熔断）
6. 数据结构与算法（正确性、复杂度可接受）
7. 模块划分与依赖（低耦合、无循环依赖）
8. 日志设计（满足排障/审计）
9. **非功能设计落地**：容量估算（QPS/存储/资源与依据）、威胁建模（信任边界/STRIDE/密钥/供应链）、可观测性（SLI/SLO/指标/追踪/健康检查/告警）、性能/安全/可扩展措施——四项缺一即 P1
10. 可追溯性（设计条目 ↔ 功能编号）
11. **任务分解合理性**（评审 `design/DEV-TASKS.md`，在设计修订完成后进行）：以模块为单位切分、可独立开发与验收、依赖显式且**无环**、并行组划分正确、**功能编号全覆盖**、未越界写优先级/排期；**任务类型（FR/ENABLER）与相对规模已标注**，ENABLER 有独立 DoD
12. **组件分层完整性**：每个组件有 `interface.md` 与 `func.md`；FUNC 超过阈值（FR > 12 或 > 300 行）已按模块拆；组件设计引用与全局 `ARCH/ARCH-NFR/DATABASE/INTERFACE/LOGGER` 一致，无重复或冲突；组件 `database.md` 未复制全局规范

## 报告格式

问题编号 `RV-DESIGN-$COMPONENT-xxx-NN`、级别（P0/P1/P2）、评审角度、位置（文件 + 章节 + fr 编号）、问题描述、修改建议、责任角色（architect）、状态。

须附**可追溯性校验结果**（功能编号 → 设计条目覆盖矩阵）；分解评审另附**功能编号 → 任务覆盖矩阵**与**依赖环检测结果**。

## 两轮时序

1. **第一轮**：评审设计文档（角度 1–10、12；组件分层完整性随首轮评）。
2. **第二轮（分解评审）**：设计修订完成后，评审 `design/DEV-TASKS.md`（角度 11）。

分解评审**并入设计评审同一门禁**，不新增独立门禁；设计评审通过是分解评审的前置。

## 闭环

报告 → 报告项目经理（经 PM 中转给架构师）→ 修改 → 评审员验证 → 关闭。

## 检查清单

- [ ] 12 个角度逐项覆盖
- [ ] 追溯矩阵无遗漏
- [ ] 分解评审：功能编号 → 任务覆盖矩阵 + 依赖环检测完成
- [ ] 组件 interface/func 分层完整，FUNC 拆分阈值合规
- [ ] DDL 与数据字典一致
- [ ] 容量/威胁建模/可观测性按判据评审（不适用须有理由）
- [ ] 结论明确
- [ ] 问题闭环

## 触发与边界

**该用**：设计产物完成、进入设计评审门禁时。

**不该用**：
- 只评审数据库设计 → 用 `datamodel-review`
- 评审需求 → 用 `prd-review`
- 评审代码 → 用 `code-review`

## 常见错误

- 只评审架构图，不校验"功能编号 → 设计条目"覆盖（漏检缺设计）。
- 结论不给"通过/不通过"。
- 建议不可执行（"性能要优化"无具体措施）。
