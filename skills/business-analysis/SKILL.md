# 业务分析（business-analysis）

## 目的与定位

从业务与用户角度描述系统需要实现的功能与业务流程，明确项目边界与模块划分。

**AI 在本技能中的价值只有三件事**：**穷举**（异常分支、边界、状态组合）、**结构化**（口语 → 泳道/状态机/决策表）、**挑刺**（找矛盾、缺口、二义性）。人工做前两件会漏，做第三件最不擅长。

**明确不做（越界即 FAIL）**：

| 不做 | 为什么 | 改为 |
|------|--------|------|
| 拍板业务规则 | 业务知识你没有，AI 也没有；编出来的规则是系统性错误 | 标 `[TBD: 待确认]` 并提问 |
| 判断组织/政治可行性 | 无信息，纯属臆测 | 列为「问题与风险」，问用户 |
| 决定优先级 | 属用户主权 | 给候选与理由，等裁定 |

## 执行者

`product-manager`

## 输入

`docs/PROJ_$PROJECT_NAME.md` + 用户材料。

### 输入分类（按优先级索取，不索取降级品）

| 级别 | 材料 | 处理 |
|------|------|------|
| **A 原始材料** | 访谈录音转写、会议纪要原文、现有系统截图、Excel 规则表、旧 PRD 草稿、工单记录 | **首选**。原样读，不做二次归纳 |
| B 二手消化稿 | 用户写的摘要、别人整理的要点 | 可用，但结论须回溯 A 求证；无 A 则标 `[推断]` |
| C 用户口述 | 对话中的描述 | 走「反向访谈」逐轮收敛 |
| D 无 | 什么都没有 | **停**，向用户索取 A（至少 C）；不得凭空填流程 |

> **禁止要求用户"先消化好再给我"**——消化会丢掉异常分支和口径差异，而这两样恰是本技能的产出。

### 必问项（只问这 4 项，其余给默认值标 `[假设]`）

| # | 必问项 | 不知道会坏什么 |
|---|--------|---------------|
| 1 | **业务目标**：这件事成功的样子是什么 | 流程正确但方向错，全部作废 |
| 2 | **角色与职责边界**：谁做、谁批、谁看、谁不管 | 泳道画错、越权设计 |
| 3 | **触发条件**：什么事件让流程开始 | 起点错 → 范围错 |
| 4 | **异常兜底责任归属**：出问题谁兜、兜不住怎么办 | 异常清单没人认领，落成死条目 |

> 其余信息（字段、时限、阈值、格式、通知方式）**给默认值并标 `[假设]`**，随文档一并请用户复核；**不逐项追问**，避免变问卷。

## 工作流（五步 + 两个门）

| 步 | 动作 | 产出 | 门 |
|----|------|------|----|
| 0 | **反向访谈**（材料不足或为 C 级时先做） | 信息补全，无独立文件 | — |
| 1 | **喂原料**：登记材料清单，标级别，登记缺口 | overview「材料清单与缺口」 | — |
| 2 | **抽骨架**：只要主干流程（角色 → 环节 → 交接），不写细节 | Mermaid 泳道主干图 | **G1 主干确认**：主干不对就停，不往下做 |
| 3 | **挖规则**：逐节点反提判断点 → 决策表 | 决策表 | **G2 规则确认**：规则错则整份下游作废 |
| 4 | **穷举异常**：逐节点问「什么情况下走不通」 | 异常场景清单 | — |
| 5 | **出规范文档**：泳道图 + 用例四段式 + 状态机 + 业务实体口径 | `ba.md` | — |

**门的纪律**：G1 / G2 必须**停下等用户答复**（留痕：「经用户确认：X」）。未答复转 `NEEDS_CONTEXT` 报项目经理，**不得自行猜答案继续**。禁止一步到位——主干错了后面全废。

## 反向访谈（Step 0，让 AI 当采访者）

不要先输出文档再让用户挑错；先问，再写。规则：

1. **一次只问 3–5 个**最关键的问题，多轮收敛，不列长问卷。
2. **优先问影响分支走向的问题**（判断条件、状态前置、谁批准、几种结果），其次才问字段与格式。
3. 用户回答暴露**矛盾、遗漏、二义性**时，**立即指出**并追问，不要记下来等最后。
4. 提问格式用 `rules/decision-brief.md` 的轻量档（`D<N> — 一句话问题` + 2–3 候选答案），成组提交。
5. 收口条件：必问项 4 项齐 + 每个主干节点都知道「谁做、什么条件走下一节点、走不通怎么办」。

## 六类产出与格式（禁止散文）

| 产出 | 用途 | 格式（硬性） |
|------|------|-------------|
| 泳道流程图 | 看清谁在什么环节做什么 | Mermaid `flowchart` + `subgraph` 按角色分泳道 |
| 用例描述 | 开发与测试依据 | **四段式**：前置条件 / 主流程 / 异常流 / 后置条件 |
| 状态机 | 实体生命周期 | 表：状态 + 触发事件 + 流转条件 + 后置状态；配 `stateDiagram-v2` |
| 决策表 | 表达复杂业务规则 | 条件列 + 规则列（R1..Rn）+ 结果列 |
| 异常场景清单 | 兜底设计 | 场景 / 触发条件 / 系统行为 / 补偿动作 / 责任人 |
| 业务实体口径 | 统一业务语言 | 实体 / 属性 / 类型 / 约束 / 业务含义 |

> 数据字典正式化（`dict.md`）属 `prd` 阶段，本技能**只出业务口径**，不写 `dict.md`——避免两处字段定义打架。

### 决策表怎么从流程里反提（本技能最值钱、最易错的一步）

1. **扫判断点**：逐节点过一遍，凡「依据某个条件走向不同结果」即判断点，全部登记（含藏在文字里的隐性判断，如"额度够就走审批"里的"够"）。
2. **拆条件**：一个判断点若有多个并列条件（角色 × 状态 × 金额区间），拆成条件列，不合并成一句话。
3. **列规则**：每个可行条件组合 = 一条规则 `R<n>`，给唯一结果。n 个二值条件需覆盖 `2^n` 个组合。
4. **标不可行**：业务上不存在的组合填 `—`，**必须写原因**（如「R5 草稿态无申请人，不成立」）。
5. **查空洞**：凡出现「其他情况按默认处理」「其余走正常流程」→ **不合格**，必须展开成明确规则。

### 异常穷举的四类问法（逐节点问，不逐流程问）

| 类别 | 问法 |
|------|------|
| 输入不合法 | 必填缺失、格式错、超范围、脏数据从哪进来 |
| 状态不允许 | 前置状态不满足时点了这个按钮会怎样 |
| 依赖失败 | 下游系统超时/报错/返回不符预期 |
| 人为中断 | 中途放弃、超时无人处理、重复提交、并发修改 |

每条异常必须给**责任人**；给不出 → `[TBD: 待确认责任人]`，进台账。

## 硬性约束（防幻觉，逐条可核对）

| # | 约束 | 违规示例 |
|---|------|---------|
| 1 | **禁止臆造业务规则**：不知道的标 `[TBD: 待确认]`，**禁止**用「通常的做法是」「一般会要求」填充 | 「通常金额超过 1 万需二级审批」← 无来源即违规 |
| 2 | **AS-IS / TO-BE 分节**，不混写；混写时全篇标 `[混合]` 并退回 | 现状流程里插入「改造后应支持批量」 |
| 3 | **每个菱形判断必须有 else 分支**：出现 `{判断}` 却只有成功一路 → 不合格 | 只画 happy path |
| 4 | **每条规则注明来源**：`来源：访谈D3 / 会议纪要 2026-10-12 / 规则表 sheet2`；无来源标 `[推断]` | 规则凭空出现 |
| 5 | **颗粒度上限**：单张流程图 ≤ **15** 节点（严于 `diagramming` 的 20），超出拆子流程 | 一张图 40 节点 |
| 6 | **`[推断]` 与 `[TBD]` 汇总成台账**，逐条等用户确认；**未确认项不得进入 `prd` 阶段**（与 `prd` 占位符机制对接） | 台账缺失或写着"待补" |

## 编号与存放

- 业务编号：`biz-$COMPONENT-$MODULE-NNN`（组件不细分模块时模块位用 `all`），一业务一编号，永不复用。
- `docs/prd/overview.md`（模版 `templates/BA-OVERVIEW.md`）
- `docs/prd/$COMPONENT/$MODULE/ba.md`（模版 `templates/BA-MOD.md`；不细分模块时省略 `$MODULE/`）

## 质量要求

- 模块划分高内聚、低耦合；模块间依赖显式列出。
- 每个业务四段式齐备（前置 / 主流程 / 异常流 / 后置），缺一不可。
- 每个判断点进决策表；每个菱形有 else；每个异常有责任人。
- 状态机闭环：每条迁移有触发条件与后置状态，非法迁移显式列出。
- 图形一律 Mermaid（细节规范见 `diagramming`）。

## 触发与边界

**该用**：把零散材料与口述转成业务语言——角色、业务、规则、异常、实体、模块边界。

**不该用**：
- 要定义功能点 `fr-` 与验收标准 → `prd`
- 要设计技术架构 → `architecting`
- 要界面原型 → `prototype`
- 要正式数据字典 → `prd`（本技能只出业务口径）

## 常见错误

- **只写 happy path**：流程图好看但没法用，异常分支一概缺失（AI 的固有倾向，必须显式对抗）。
- **颗粒度失控**：不设节点上限就越写越细，最后维护不起。
- **把推断当事实**：`[推断]` 项未逐条人工确认就当结论用——这是 BA 不可让渡的责任。
- **判断点藏在流程文字里**：不进决策表，下游 PRD 必然写出一批"按规则校验"的废话。
- **业务无编号或一号多业务**；编号写成 `biz-xxx` 这类不可机械解析的形式。
- **越界拍板**：自行决定业务规则或优先级。
