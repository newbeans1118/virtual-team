# PRD 编写（prd）

## 目的

生成 PRD，使业务分析落地为可实现、可验收的功能需求。

## 执行者

`product-manager`

## 输入

- `docs/prd/overview.md`、`docs/prd/$COMPONENT/$MODULE/biz.md`（组件不细分模块时 `docs/prd/$COMPONENT/biz.md`）
- `docs/PROJ_$PROJECT_NAME.md`

## 输出

- `docs/prd/$COMPONENT/$MODULE/prd.md`（模版 `templates/PRD-MOD.md`；组件不细分模块时省略 `$MODULE/`）
- `docs/prd/prd-nonfunc.md`（模版 `templates/PRD-NONFUNC.md`）
- `docs/prd/dict.md`（模版 `templates/DICT.md`；实体标注所属组件/模块）
- `docs/prd/$COMPONENT/$MODULE/trace/prd.json`（结构化分片，经 `prd-structure`）
- `docs/prd/RTM.md`（模版 `templates/RTM.md`）

## 流程

1. **功能点定义**：为每个功能点定义 —— 编号 `fr-$COMPONENT-$MODULE-NNN`（固定 4 段；组件不细分模块时模块位用 `all`）、功能名称、操作的用户、输入、输出、处理逻辑、约束条件、**验证标准**（可独立验收）。验证标准必须**条列化且 GWT 化**——每条为一个 `{key, given, when, then, kind}` 结构（见 `prd-structure` 的 acceptance 结构）。**整段文本、或只有 `then` 无 `given/when` 的验收标准不合格**——无法逐条核对覆盖。
   - 生成条件时**对照下方「acceptance 条件生成清单」**，按适用性取舍（不适用的类别可省略，但**省略应有理由**）。
   - 定义完成后**按下方「FR 粒度五条检验」自查**，不通过则拆分或降层。
2. **业务-功能关联**：为每个 `biz-xxx` 说明由哪些功能点、如何实现，产出一张关联矩阵。
3. **功能归模块**：先划分**组件**（`$COMPONENT`，系统的高层可部署/实现单元），再按关联紧密程度把功能分配到组件内的**模块**（`$MODULE`）；组件较小时可不细分模块（模块位用 `all`）。
4. **数据字典**：定义业务实体、字段、类型、约束、状态枚举。
5. **非功能需求**：安全需求、性能需求（量化指标）。
6. **一致性校验**：确认所有 biz-xxx 均被 fr 覆盖；产出 RTM（含页面/原型列）。

## L1–L4 四层结构（粒度归属，硬性）

| 层 | 内容 | 载体 |
|---|------|------|
| **L1 能力域** | 「用例管理」「执行」等模块分组 | PRD 章节标题 |
| **L2 功能点（FR）** | **一个可独立验收的行为闭环——粒度定在这一层** | 功能需求章，统一编号 `fr-$COMPONENT-$MODULE-NNN` |
| **L3 验收标准** | 一条 FR 配若干条 GWT（Given/When/Then） | FR 内部（acceptance 条列） |
| **L4 交互/视觉细节** | 按钮态、文案、动效、颜色、布局 | 原型 + 交互说明，**禁止写入 FR** |

> **降层规则**：内容属 L4（按钮状态/文案/样式/布局）**不得**出现在 FR 中——移到原型与交互说明。FR 只描述"做什么行为、什么可观察结果"。

## FR 粒度五条检验（定义完成后逐条自查）

一个 FR = **单一触发 → 单一可观察结果** 的完整行为闭环。按序通过以下五条检验，**否则拆分或降层**：

1. 描述中出现「以及」「同时还要」→ **拆分**；
2. 可被一组测试用例独立覆盖，验收**不依赖另一条 FR** → 否则**拆分**；
3. 可独立排期、独立指派、独立标记完成 → 否则**拆分或合并**；
4. 一句话说不清 → 太粗，**拆分**；
5. 内容是按钮状态、文案、样式 → 太细，**降层到 L4**。

**自检技巧（先写 GWT 再回填）**：写完描述先写 GWT，再回填 FR 描述。若一条 FR 的多个 GWT 出现**两种不相干的 `when`（用户操作）**，即为**拆分信号**。

## acceptance 条件生成清单（逐类对照，按适用性取舍）

生成一个功能点的 acceptance 时，**逐类自查**；不适用的类别可省略（省略须在条件列表外一句说明，如"本功能无权限维度"）。类别是**写作思维提示**，最终 `kind` 仍只能取 `normal/boundary/negative`（下表给出映射）。

| # | 类别 | 说明 | 归入 kind |
|---|------|------|-----------|
| 1 | **正常路径** | 主流程成功，输入合法且状态允许 | `normal` |
| 2 | **边界值** | 数值/长度/时间/容量的临界（最小值、最大值、越界各一） | `boundary` |
| 3 | **异常路径** | 非法输入、错误状态、依赖失败等失败路径 | `negative` |
| 4 | **权限校验** | 有权限应通过 / 无权限应被拒 / 越权应被拦 | `normal`（通过）/ `negative`（拒绝） |
| 5 | **输入校验** | 必填缺失、格式错误、超长、类型不符 | `negative`（非法）/ `boundary`（临界） |
| 6 | **状态约束** | 非法状态迁移应被拒（如未审核不可发布） | `negative` |

> **取舍原则**：只写"该功能点自己该验的行为"。系统级的安全/性能约束（加密算法、防注入机制、审计日志格式）**不写在此处**——它们属 `prd-nonfunc.md` 的 `NF-S-xxx`/`NF-P-xxx`。
>
> **NFR 可执行性**：每条 NF 须写清目标值、负载/场景、测量点、验证方式（见 `templates/PRD-NONFUNC.md`）；NFR 由 `nfr-testing` 独立评估，**不进入 FR acceptance**（两轨不混写）。
>
> **示例**（用户注册功能点）：
> ```
> c1 (normal)   Given 合法邮箱与合规密码 / When 提交注册 / Then 注册成功且落库
> c2 (boundary) Given 邮箱长度=254（上限） / When 提交注册 / Then 仍可注册
> c3 (negative) Given 邮箱已占用 / When 提交注册 / Then 拒绝且不落库
> c4 (negative) Given 未登录访客 / When 调用管理接口 / Then 403 拒绝      ← 权限校验
> c5 (boundary) Given 密码长度=7（低于下限8） / When 提交注册 / Then 拒绝  ← 输入校验
> ```

## 前后台 PRD 边界（配合业务规则占位符原则）

**组件级 PRD 为主**（组件 = `$COMPONENT`）；组件过大时按**逻辑边界**进一步拆为模块级 PRD（拆分依据是业务逻辑内聚，不是数量）。

**前后台拆分判据（硬性）**：**存在 UI 交付，且业务规则由独立服务承载**（前后端分离架构 / 后端独立部署）→ **必须拆** `prd-ui.md` / `prd-svc.md`；纯后端（无 UI）或纯静态前端（无独立业务服务）→ 用单份 `prd.md`，不拆。

- **前台 PRD**（`prd-ui.md`）：FR 只约束 **UI 行为与前端校验**；涉及业务规则一律以 `【占位：待<服务名>PRD 补充·<规则名>】` 引用，**不自定义规则**。
- **后台服务 PRD**（`prd-svc.md`）：FR 约束**业务规则、数据模型与接口契约**，不写 UI。
- 同一页面在前后台两份 PRD 中**各自沿自己的轴切分**，内容不重叠、编号不重复（用模块位 `ui` / `svc` 区分，如 `fr-workbench-ui-001` / `fr-workbench-svc-001`）。

## 数量与拆分原则

- 功能点**数量不设硬性数值限制**，以模块/能力域自然划分为准：模块边界清晰即成一章，**不强行按数量拆分或合并**文档与章节。
- 仅保留两条硬性项：
  1. **每条 FR 必须配 GWT 验收**（条数以覆盖主流程 + 边界 + 异常为准，不设上限、不为凑数堆砌）；
  2. 单条 FR 若因过大而**无法独立验收**，仍须按「五条检验」拆分——**拆分依据是行为闭环边界，不是数量阈值**。

## 质量要求

- 功能点"可独立验收"是硬门槛：无法验收的不要列为功能点（降级为约束或说明）。
- 每个功能点必须有**验证标准**，且**条列化 + GWT 化**（每条 `{key, given, when, then, kind}`）——测试工程师据此出用例，`test-rebuild` 据此算测试点级覆盖。**整段文本或缺失 GWT 不合格**。
- **FR 粒度经五条检验**；L4 交互细节不得写入 FR。
- **acceptance 条件按「生成清单」逐类对照**（正常/边界/异常/权限/输入校验/状态约束），不适用的类别可省略但须有理由；漏掉适用类别 = 需求不完备。
- **前后台边界清晰**：前台不定义业务规则（用占位符引用），后台不写 UI。
- **禁止"部分完成"语义**：粒度不合适导致的半完成，按「五条检验」拆分解决，不允许降粒度凑整。
- 规格必须**覆盖**业务分析的全部内容（追溯完整）。
- 非功能需求"不遗漏、不过分"：性能指标须有依据。

## 输出：追溯矩阵（示例）

| 业务编号 | 业务名称 | 覆盖功能点 | 组件 | 模块 |
|---------|---------|-----------|------|------|
| biz-workbench-task_list-001 | 用户注册 | fr-workbench-task_list-001, ... | workbench | task_list |

> **RTM（PRD 追踪矩阵）**：包含「页面/原型」列，见 `templates/RTM.md` 与 `prototype` 技能的「页面 × FR 覆盖矩阵」。

## PRD 文件命名与存放

- **存放目录**：`docs/prd/$COMPONENT/$MODULE/`（组件不细分模块时省 `$MODULE/`）——底稿与正式 PRD 同目录。
- **命名**（沿用现有体系，按层级取用）：
  - 组件级：`prd.md`（如 `docs/prd/workbench/prd.md`）；前后台拆分时 `prd-ui.md` / `prd-svc.md`；
  - 模块级（组件过大时按逻辑拆）：放该组件下的模块子目录。
- **组件名/模块名一律 snake_case 英文**（小写字母/数字/下划线，**禁含连字符**——连字符是层级分隔符），优先取 docker-compose 服务名与已有底稿中的英文名；**未定义时先询问用户，不得自行杜撰**。
- **文件名一经确定不轻易改名**；确需改名必须同步更新项目记忆、RTM、原型及全部引用路径。

## 检查清单

- [ ] 所有 biz-xxx 被 fr 覆盖（矩阵无空行）
- [ ] 每个功能点有验证标准，且**条列化 + GWT 化**（key/given/when/then/kind）
- [ ] **FR 粒度经五条检验**；无「以及/同时还要」式复合 FR；无 L4 细节混入
- [ ] acceptance 条件**按生成清单逐类对照**（正常/边界/异常/权限/输入校验/状态约束），不适用类别已说明理由
- [ ] **前后台边界清晰**（前台业务规则用占位符，后台不写 UI）
- [ ] 数据字典与业务实体一致
- [ ] 非功能需求量化
- [ ] PRD 覆盖 biz 全部内容
- [ ] RTM 已产出（含页面/原型列）

## 触发与边界

**该用**：业务已分析清楚，要把它转成可实现、可验收、可追溯的功能需求。

**不该用**：
- 业务还没建模 → 先用 `business-analysis`
- 要评审需求 → 用 `prd-review`
- 要结构化存储功能点供追踪 → 用 `prd-structure`

## 常见错误

- 功能点"不可独立验收"却列为功能点（应降级为约束或说明）。
- 功能点没写**验证标准**，测试无法出用例。
- **acceptance 只写正常路径**，漏边界/异常/权限/输入校验/状态约束（对照生成清单逐类自查）。
- **一条 FR 塞多个不相干行为**（「以及/同时还要」、多个不相干 when）——应拆分。
- **把按钮态/文案/样式写进 FR**（应降层到 L4 原型与交互说明）。
- **前台 PRD 自定义业务规则**（应用 `【占位】` 引用后台 PRD）。
- 有 biz 无对应 fr（追溯断裂），或凭空加 fr。
- 非功能需求不量化（"性能要好"无意义）。
