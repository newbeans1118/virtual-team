# 产品发布（releasing）

## 目的

两阶段交付构建物：**测试版构建**（测试准入条件，测试环境来源）与**生产版发布**（验收通过后的正式交付）。

## 执行者

`release-engineer`

## 阶段一 · 测试版构建（代码评审闭环后）

**前置（硬性）**：

1. 全部开发任务的代码评审已闭环（无未关闭 P0/P1）。
2. 主干含全部通过代码评审的任务 commit（任务完成即 commit，见 `rules/engineering-discipline.md` §13）。
3. **同一 commit 全量 verify 通过**（`scripts/verify.sh`，日志留档；契约见 §14）。

**流程**：

1. **全新 worktree 构建**：从 git 主干拉取到独立 worktree，从头构建（避免工作区脏状态污染）。
2. **编译**：按 `design/ARCH.md` 的构建系统编译。
3. **打包**：生成发布组件（含版本号、commit、依赖清单），归档到 `release/artifact/`。
4. **手册**：用 `skills/doc-writing` 产出 `release/manual-install.md`（安装手册）与 `release/manual-release.md`（发布手册）——**手册基于真实构建产物编写**。
5. **部署验证**：在目标环境部署，执行冒烟测试，记录验证命令与结果。
6. **标记测试版**：未经四方联合确认的构建即测试版——该产物（build/commit）是测试环境与 `RUN.envs` 的**证据来源**。

> **测试期缺陷修复后**：按 PM 派发重新执行阶段一（回归轮的 envs 引用新 build/commit）。

## 阶段二 · 生产版发布（项目验收通过后）

**前置（硬性）**：项目验收评审通过（`review/project/RV-PROJ-ACCEPT.md`）。

**流程**：

1. **四方联合确认**：产品经理、测试经理、架构师、代码评审员联合确认。
2. **发布计划**：按 `templates/RELEASE-PLAN.md` 产出 `release/RELEASE-PLAN-<version>.md`——部署策略、DB 迁移顺序、回滚方案、发布后验证窗口。
3. **制品完整性**：生成 `SHA256SUMS` 与 `sbom.json`（依赖 + 版本 + 许可证），归档 `release/artifact/`。
4. **回滚演练**：生产版发布前在测试环境执行一次回滚，记录时间/结果；未演练不得发布。
5. **构建决策**：测试期无代码变更 → 测试版构建直接升级标记；有变更 → 重新构建（回到阶段一）再确认。
6. **打标签并发布**：`git tag` 打在主干 commit 上，按计划执行部署（含 DB 迁移顺序）。
7. **发布后验证**：≥30 分钟窗口，按计划检查错误率 / P95 / 关键业务量；超阈值立即回滚（release-engineer + PM 决策），结论写入发布计划。

## 输入 / 输出

- **输入**：`src/`、`design/`、各阶段评审结论、`test/report/`
- **输出**：
  - 测试版/生产版构建组件 `release/artifact/`
  - `release/manual-release.md`、`release/manual-install.md`
  - 发布计划 `release/RELEASE-PLAN-<version>.md`（策略/迁移/回滚/发布后验证）
  - 制品完整性文件 `release/artifact/SHA256SUMS`、`release/artifact/sbom.json`
  - 部署验证记录 + 回滚演练记录 + 发布后验证结论 + 版本标签（生产版）

## 约束（硬性）

- build 必须用全新 worktree，从 git **主干**拉取从头构建。
- 发布组件必须**可复现**：记录版本、commit、构建命令、依赖版本。
- 未经四方联合确认的产物**只能标记为测试版**，不得作为生产版发布。
- 生产版必须打标签。
- **测试环境必须来自测试版构建产物**（与发布形态同源）——不得用开发工作区直接部署充当测试环境。
- **构建前须全量 verify 通过**：在 worktree 对同一 commit 执行 `scripts/verify.sh`，失败不得打包（契约见 discipline §14）。
- **制品完整性**：发布组件必须附 `SHA256SUMS` 与 `sbom.json`（依赖/版本/许可证）；缺失不得发布。
- **回滚可执行**：生产版发布前必须完成一次回滚演练；无演练记录不得发布。
- **发布后验证**：生产版发布后须执行 ≥30 分钟验证窗口，超阈值回滚并记录。

## 检查清单

**阶段一（测试版构建）**
- [ ] 前置满足（代码评审闭环、主干含全部 commit）
- [ ] 全新 worktree 构建成功
- [ ] 组件归档且可复现（版本/commit/构建命令/依赖）
- [ ] 同一 commit 全量 verify 通过（`scripts/verify.sh`，日志路径记入构建元数据）
- [ ] 安装/发布手册已产出（基于真实构建）
- [ ] 部署冒烟验证通过（附命令与结果）
- [ ] 已标记测试版（build/commit 证据可供 RUN.envs 引用）

**阶段二（生产版发布）**
- [ ] 项目验收评审已通过
- [ ] 四方联合确认完成
- [ ] 发布计划已产出（策略/迁移/回滚/发布后验证）
- [ ] 制品含 SHA256SUMS 与 SBOM
- [ ] 回滚演练已执行并记录
- [ ] 构建决策已执行（直接升级 / 重新构建）
- [ ] 已打 tag
- [ ] 发布后验证窗口已执行，结论已记录

## 触发与边界

**该用**：代码评审闭环后的**测试版构建**；验收通过后的**生产版发布**。

**不该用**：
- 代码评审未闭环 → 不构建测试版
- 验收未通过 → 禁止生产版发布
- 只写安装/发布手册 → 用 `doc-writing`（手册产出归 doc-writing，本技能调用它）

## 常见错误

- 在脏工作区直接构建（必须全新 worktree）。
- 代码评审未闭环就构建测试版（未评审代码进入测试 = 门禁失效）。
- 用开发工作区充当测试环境（与发布形态漂移；必须走测试版构建产物）。
- 未经四方联合确认就标"生产版"（违规）。
- 发布物不可复现（未记录版本/commit/构建命令/依赖）。
- 部署不验证就宣称"能跑"（违背证据先于结论）。
- 测试期修复缺陷后忘记重新构建（回归轮 envs 引用旧 build，结论失真）。
