# 代码评审（code-review）

## 目的

独立评审代码：先确认**实现是否符合规格**，再评估**质量/安全/性能**。产出可定位、可闭环的评审报告。

## 执行者

`code-reviewer`

## 输入

- `src/` 下代码
- `build/verify/latest.log`（评审前须为当前 commit 的全量通过日志；契约见 discipline §14）
- 各组件/模块 `prd.md`、`docs/prd/$COMPONENT/$MODULE/trace/prd.json`（功能编号来源）
- `design/`（FUNC / INTERFACE / DATABASE / LOGGER）

## 输出

- `review/code/CR-CODE-xxx.md`（问题定位到**文件 + 模块 + 功能编号**）

## 两阶段评审（顺序不可颠倒）

> 必须先做规格符合性，再做质量。混在一起评会导致漏检规格。

### 阶段一 · 规格符合性

- 逐条核对 `fr-$COMPONENT-$MODULE-NNN`：**是否全部实现**。
- **是否多做**：规格/设计之外的代码 → 记为冗余（P2）或风险。
- **是否漏做**：规格要求但未实现 → P0/P1。
- 结论：`规格符合` / `规格不符`。

### 阶段二 · 代码质量（规格通过后才做）

| 维度 | 检查点 |
|------|--------|
| 正确性 | 与设计一致；边界、异常、并发是否处理 |
| 质量 | 冗余、重复逻辑、死代码、过深嵌套、命名混乱 |
| 安全 | SQL/命令注入、XSS、越权、敏感信息落盘、内存泄漏、死锁、资源未释放、反序列化 |
| 性能 | N+1 查询、无索引全表扫描、无界缓存、锁粒度过大、重复计算 |
| 可维护 | 是否满足最简原则，有无过早抽象 |

## 报告格式

| 问题编号 | 阶段 | 级别 | 位置（文件:行 + 模块 + fr 编号） | 问题描述 | 修改建议 | 状态 |
|---------|------|------|--------------------------------|---------|---------|------|
| CR-CODE-xxx-01 | 规格/质量 | P0 | | | | 待处理 |

须给出**两个阶段的独立结论**与总体结论（通过 / 不通过）。

## 缺陷修复评审（单阶段，P0/P1）

**触发**：`BUG.severity ∈ {P0,P1}`，修复 commit 已产生，重建测试版之前。

**五项检查**（只评修复 diff，不做全量规格核对）：

1. **改动范围**：仅含缺陷相关文件；无关重构/格式化 → 打回
2. **根因**：修复针对根因；症状掩盖（try/catch、特判）→ 打回
3. **回归影响**：接口/数据/共享逻辑的影响面已评估
4. **测试**：新增可复现缺陷的测试（修复前失败、修复后通过）
5. **新风险**：未引入安全/性能/兼容问题

**输出**：短报告 `review/code/CR-FIX-<BUG-id>.md`（结论 + 五项 + 问题），结论回填 `BUG.fix.review`。

**门禁**：未 pass 不得重建测试版、不得进入回归；P2 豁免（可抽样）。

## 闭环

报告 → 报告项目经理（经 PM 中转给责任工程师）→ 修订 → 评审员验证 → 关闭。未关闭 P0/P1 阻塞进入测试。

## 约束

- **只读代码，不得修改**。必要时可运行验证，但不得改动被评审物。
- 结论必须可定位、可复现；禁止"代码质量差"这类泛泛之谈。
- **核对 verify 真实性**：日志首行 commit 与评审对象一致；相关步骤不得为 SKIP；测试用例数 > 0。
- 遵循 `rules/engineering-discipline.md` 的证据先于结论。

## 常见错误

- 只评质量不做规格核对（漏检缺功能/多实现）。
- 报告问题不给定位，开发无法修改。
- 只报告不跟踪，评审未闭环。
- 把主观风格偏好当缺陷（应区分 P0/P1 与 P2 建议）。
