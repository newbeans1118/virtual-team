# 架构设计（architecting）

## 目的

设计系统架构、组件及内外接口，以及组件之间的相互关系。

## 执行者

`architect`

## 输入

- `docs/PROJ_$PROJECT_NAME.md`
- `docs/prd/$COMPONENT/$MODULE/prd.md`、`prd-nonfunc.md`

## 输出

- **`design/ARCH.md`**（开发者必读）：技术栈、系统架构、组件设计、交互时序、部署视图、ADR、追溯
- **`design/ARCH-NFR.md`**（架构/评审/测试/发布读）：非功能支撑、容量估算、威胁建模、可观测性

## 内容要求

1. **技术栈选型**：语言/框架/中间件/存储，每项给理由 + 被否决的备选与原因。
2. **系统架构**：Mermaid 架构图（分层/组件）。
3. **组件设计**：每个组件的职责、输入、输出、依赖。
4. **组件交互**：关键流程 Mermaid 时序图。
5. **部署视图**：部署拓扑、环境划分。
6. **接口概述**：内部/对外接口清单（细节见 INTERFACE.md）。
7. **[ARCH-NFR] 对非功能需求的支撑**：性能、安全、可用性、可扩展性的架构级措施。
8. **[ARCH-NFR] 容量与资源估算**：峰值 QPS/并发/存储/带宽/计算资源，附估算依据与验证方式（判据见 `templates/ARCH-NFR.md` §2）。
9. **[ARCH-NFR] 安全设计（威胁建模）**：信任边界 + STRIDE + 认证授权 + 密钥管理 + 依赖供应链（§3）。
10. **[ARCH-NFR] 可观测性设计**：SLI/SLO、指标/追踪、健康检查、告警路由（§4；日志详设归 `LOGGER.md`）。
11. **组件设计索引**：组件 → `design/$COMPONENT/interface.md` / `func.md` / `database.md`（ARCH §3.1）。
12. **可追溯性**：架构决策关联到模块/功能编号，并指向设计文件/章节。

## 质量要求

- 每个架构决策必须可追溯到需求或约束。
- 拒绝过度设计：无需求支撑的组件/抽象不纳入。
- 依赖方向清晰，禁止循环依赖。
- 容量/威胁建模/可观测性按判据必填，缺项须写"不适用 + 理由"（写在 `ARCH-NFR.md`）。
- **两个文件不互相重复**：`ARCH.md` 不写容量/威胁/可观测细节，`ARCH-NFR.md` 不重复技术栈与组件。
- 图形一律 Mermaid。

## 检查清单

- [ ] 技术选型含理由与备选对比
- [ ] 架构图 + 组件交互时序图齐备
- [ ] 组件职责与依赖明确
- [ ] 部署视图齐备
- [ ] 非功能支撑措施到位
- [ ] 组件设计索引齐全（interface/func/database）
- [ ] 容量估算齐全（QPS/并发/存储/带宽/资源）
- [ ] 威胁建模齐全（信任边界 + STRIDE + 密钥/供应链）
- [ ] 可观测性齐全（SLI/SLO + 指标/追踪/健康检查/告警）

## 触发与边界

**该用**：需求定稿后定架构与技术方案。

**不该用**：
- 设计数据库表 → 用 `data-modelling`
- 设计接口/算法/日志/模块功能 → 用 `general-design`
- 评审架构 → 用 `design-review`

## 常见错误

- 技术选型不给理由、不列被否决的备选。
- 过度设计：无需求支撑的组件/抽象。
- 组件间循环依赖或依赖方向混乱。
- 架构决策无法追溯到需求编号。
