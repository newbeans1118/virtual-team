# 架构设计（architecting）

## 目的

设计系统架构、组件及内外接口、组件间关系；关键决策留痕可追溯。

## 执行者

`architect`

## 输入

- `docs/PROJ_$PROJECT_NAME.md`
- `docs/prd/overview.md`（外部角色/系统，供上下文视图）
- `docs/prd/$COMPONENT/$MODULE/prd.md`、`prd-nonfunc.md`

## 输出

- **`design/ARCH.md`**（所有系统必产出）：上下文、技术栈与决策表、架构图、组件设计、交互、部署、跨边界接口、关键 NFR 与场景表、追溯
- **`design/ARCH-NFR.md`**（**仅分布式档**产出）：容量与成本、威胁建模、可观测性详述

> 轻量档不单独出 ARCH-NFR.md，关键 NFR（性能目标、安全基线）直接写进 ARCH.md，避免小项目产出近空文件。

## 规模分档（先定档，再按档写）

按以下规则自判，写进 ARCH.md 开头：

| 档位 | 判定条件（满足任一即入档） | 必填范围 |
|---|---|---|
| **轻量档** | 单体应用 / 内部工具 / 单数据源 / 无高并发要求 | 内容要求 §1-9 |
| **分布式档** | ≥2 个独立部署单元 / 多数据源 / 明确高并发（峰值 QPS 有量级要求）/ 跨系统集成 | 内容要求 §1-13 |

**规则**：档内必填项最多允许 2 处标"不适用 + 一句话理由"。超过 2 处，说明档位选错，重定档，不得靠套话糊过去。

## 内容要求

### 通用必填（两档都要）

1. **系统上下文**：外部角色、外部系统、系统边界；一张上下文图。
2. **技术栈选型**：语言/框架/中间件/存储，每项给理由 + 被否决的备选（记入决策表，见下）。
3. **系统架构**：分层/容器图（Mermaid）。
4. **组件设计（含索引）**：每个组件的职责、输入、输出、依赖；给出 `design/$COMPONENT/interface.md` / `func.md` / `database.md` 索引。
5. **组件交互**：关键流程时序图（Mermaid）。
6. **部署视图**：部署拓扑、环境划分。
7. **跨边界接口概述**：仅列**跨越架构边界**的接口；细节指向 `INTERFACE.md`，不在此重复。
8. **关键 NFR 与场景表**：列出关键非功能需求，用简表表达，作为验收判据：

   | 场景 | 目标指标 | 验证方式 |
   |---|---|---|
   | 例：峰值下单 | P95 < 200ms | 压测报告 |

   > 轻量档只写真正影响架构的 NFR（通常 2-4 条），不追求覆盖全。
9. **可追溯性**：决策关联 FR 编号（来源 `docs/prd/`），并指向设计文件/章节。

### 分布式档追加

10. **集成与通信风格**：同步 REST/gRPC vs 异步消息、API Gateway、消息队列选型的决策与理由。
11. **数据架构**：数据在组件间流转、一致性模型（ACID/BASE）、分布式事务或事件流策略；与 `data-modelling`（表结构）的边界。
12. **韧性设计**：超时、重试、熔断、降级、故障隔离与依赖方向。
13. **容量与成本**：峰值 QPS/并发/存储/带宽估算（附依据）；成本**粗估**（标明"非承诺"）。

## 决策记录（轻量，不搞 ADR 流程）

关键决策在 ARCH.md 内用一张表留痕，**不要求独立 ADR 文件、不要求逐条编号仪式**：

| 决策 | 备选方案 | 选择理由 | 关联 FR |
|---|---|---|---|
| 选 PostgreSQL | MySQL / MongoDB | 事务强一致 + JSONB 够用 | FR-xxx |

> 只记**影响架构走向**的决策（通常 3-8 条）。日常技术细节不入表。

## 质量要求

- 每个架构决策可追溯到需求或约束（决策表 + §9）。
- 拒绝过度设计：无需求支撑的组件/抽象不纳入。
- 依赖方向清晰，禁止循环依赖。
- 档内必填项缺项须写"不适用 + 理由"，且全文档不超过 2 处。
- **两文件不脱节**：ARCH.md 的 NFR 结论与 ARCH-NFR.md 详述必须一致，不得一处说"满足"另一处说"未覆盖"。
- 图形默认 Mermaid；复杂上下文图/容器图如 Mermaid 表达不清，可用 PlantUML，并说明。
- **篇幅**：ARCH.md 正文控制在可读范围（建议约 8-10 页等效），细节外链到组件文件，不堆在 ARCH。

## 检查清单

**通用**
- [ ] 已定档并写明判定依据
- [ ] 上下文图（外部角色/系统/边界）齐备
- [ ] 技术栈 + 决策表（含备选与理由）
- [ ] 架构图 + 关键交互时序图齐备
- [ ] 组件职责/依赖明确，组件索引齐全
- [ ] 部署视图齐备
- [ ] 跨边界接口清单指向 INTERFACE.md
- [ ] NFR 场景表（场景/指标/验证）齐备
- [ ] 决策可追溯 FR
- [ ] "不适用"标注 ≤ 2 处

**分布式档追加**
- [ ] 集成/通信风格决策明确
- [ ] 数据架构（流转/一致性/分布式事务）明确
- [ ] 韧性设计（超时/重试/熔断/降级）到位
- [ ] 容量估算 + 成本粗估齐备
- [ ] ARCH-NFR.md 已产出且与 ARCH.md 结论一致

## 触发与边界

**该用**：需求定稿后定架构与技术方案。

**不该用**：
- 设计数据库表 → 用 `data-modelling`
- 设计接口/算法/日志/模块功能 → 用 `general-design`
- 评审架构 → 用 `design-review`

## 常见错误

- 技术选型不给理由、不列备选。
- 过度设计：无需求支撑的组件/抽象。
- 组件间循环依赖。
- 决策无法追溯到需求编号。
- 漏画系统上下文，直接从内部组件开设计。
- 小项目硬上分布式档的熔断/分布式事务/容量模型，产出大量"不适用"套话。
- 为凑清单把 NFR 写成措施罗列，无指标、无验证方式。
- 只给目标态，棕地改造不写迁移与回滚路线。
